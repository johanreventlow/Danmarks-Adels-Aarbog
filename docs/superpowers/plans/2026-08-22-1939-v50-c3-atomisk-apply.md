# 1939 v50 C3 Atomic Apply Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a hash-bound, human-approved, atomic and reversible C3 apply pipeline for exactly the five fully resolved cases, ending with disposable apply/reversal proof and no production mutation.

**Architecture:** A Python candidate builder selects whole resolved cases and normalizes five record texts; a read-only R/DBI preview measures live IDs and before-state; a Python finalizer and local HTML produce a text-free approval artifact. Dedicated private PostgreSQL batch tables and public gated RPCs apply all five cases in one transaction, while an R gateway handles authorization, commit-unknown recovery, disposable rehearsal, and reversal.

**Tech Stack:** Python 3.9.6 stdlib/pytest, R/DBI/testthat/jsonlite, PostgreSQL 17 PL/pgSQL, Supabase Auth/RLS, vanilla HTML/JavaScript, Playwright Chromium.

**Spec:** `docs/superpowers/specs/2026-08-22-1939-v50-fase-c3-apply-design.md`

**Prerequisite:** `docs/superpowers/plans/2026-08-22-1939-v50-c3-identitetsinvarianter.md` is fully implemented, independently reviewed, and green.

## Global Constraints

- Only five whole cases are selected: five `different`, five `assign`, one `no_publication`; both axes of the other two cases are absent.
- Real narrative text stays under ignored `work/task27-1939-v50-c3-apply/` and is never printed, committed, screenshotted, or opened by model/browser tools.
- All Python commands use `/usr/bin/python3`; code is Python 3.9 compatible.
- All five `PGDATABASE`, `PGHOST`, `PGPORT`, `PGUSER`, and `PGPASSWORD` are set together or all omitted.
- No task may mutate production. Task 9 stops after disposable apply/reversal and requests a new production GO.
- Public privileged functions have fixed search paths, explicit role gates, explicit revokes, and only the minimum grants.
- Every write batch is one server-side call and one database transaction; no client-side loop is an apply boundary.
- Every task uses TDD, focused verification, independent spec review, independent quality review, and a separate commit.
