# Placement, identitet, promotion og lineage Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Gør placement- og promotionlivscyklusser reelt versionerbare, ensret identitetsinvarianterne og gør cross-clan lineage-mapping umulig i databasen.

**Architecture:** Placements består af immutable forslag plus append-only beslutningsevents og current-views. Promotionregler består af immutable versioner under en stabil regellinje, mens identitets-RPC'en selv håndhæver mention- og targetkrav. Lineage-slægt håndhæves med sammensatte fremmednøgler.

**Tech Stack:** PostgreSQL 17, PL/pgSQL, Supabase-schema/RLS, `dblink`, `schema.sql`, `db-migrations.sql` og `db-verify.sql`.

## Global Constraints

- Bevar append-only audit og eksisterende effektiv tilstand; migrationen må ikke gætte eller omskrive en konflikt.
- `schema.sql` og `db-migrations.sql` skal have semantisk identiske slutdefinitioner.
- Alle writers og lockordener spores; en sekventiel test er ikke bevis for en concurrent invariant.
- Nye private tabeller følger repoets eksisterende deny-by-default/RLS-mønster, men dette arbejde er ikke et bredt sikkerheds- eller GDPR-review.
- Frisk schema -> migrations -> migrations igen er obligatorisk PostgreSQL-17-gate.
- Ingen produktionsdatabase, re-import, deployment, push eller `load_daa.R`-ændring.

- [ ] **Step 3: Implementér fresh-schema eventmodel**

Omdøb basekolonnerne til `initial_status`. Tilføj `id uuid DEFAULT gen_random_uuid()` som primærnøgle på persona-placement og flyt den gamle kompositte nøgle til en `UNIQUE`-constraint. Begge initial-statuschecks bruger `('proposed','accepted','rejected','superseded')`.

Begge decisiontabeller følger denne form med den relevante FK:

```sql
CREATE TABLE private.source_record_placement_decision (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  placement_id uuid NOT NULL REFERENCES private.source_record_placement(id),
  version integer NOT NULL CHECK (version>=1),
  decision_status text NOT NULL CHECK (decision_status IN ('proposed','accepted','rejected','superseded')),
  evidence jsonb NOT NULL CHECK (jsonb_typeof(evidence)='object' AND evidence<>'{}'::jsonb),
  decision_origin text NOT NULL CHECK (decision_origin IN ('ingest','migration','redaction')),
  decided_by uuid,
  decided_by_name text NOT NULL CHECK (btrim(decided_by_name)<>''),
  decided_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (placement_id,version),
  CHECK (decision_origin<>'redaction' OR decided_by IS NOT NULL)
);
```

Persona-eventtabellen bruger `placement_id -> source_persona_placement(id)`. Begge får append-only trigger, RLS og samme private ACL som de eksisterende evidenstabeller.

Current-views bruger `DISTINCT ON (placement_id) ... ORDER BY placement_id,version DESC` og joiner beslutningen med forslagsrækken. Alle reads i persona-detail, promotionvalidering og locks skiftes til views og `decision_status='accepted'`.

- [ ] **Step 4: Implementér transition-RPC'erne og lockorden**

Begge RPC'er følger identity-RPC'ens actor-, expected-version- og append-only-mønster. Tilladte transitions er:

```sql
(v_current_status='proposed' AND p_status IN ('accepted','rejected'))
OR (v_current_status='accepted' AND p_status='superseded')
```

Record-placement writer låser først parent `source_record`, derefter placement-ID. Persona-placement writer låser først `source_persona`, derefter record-placement og persona-placement; dette matcher promotionens persona -> placement-rækkefølge. Ved accept kontrolleres current-viewet under parentlåsen, så to samtidige forslag ikke kan blive accepteret for samme forretningsnøgle.

Nye forslagsfunktioner indsætter baseforslag og version 1 `proposed`-event atomisk. En deferred constraint trigger afviser en baseplacement uden mindst ét event ved commit.

- [ ] **Step 5: Implementér fail-closed migration/backfill**

Migrationen:

1. tilføjer surrogate persona-placement-ID og udfylder det;
2. opretter eventtabeller/views;
3. indsætter præcis ét version 1-event pr. eksisterende række med `decision_origin='migration'`, `decided_by_name='legacy placement backfill'` og evidens med den gamle status;
4. sammenligner antal og accepterede ID-sæt før/efter;
5. skifter consumers;
6. omdøber `status` til `initial_status` og fjerner `source_record_placement_active_uidx`.

Ved ukendt status, manglende event eller ændret accepted-sæt rejses `EVIDENCE_PLACEMENT_BACKFILL_MISMATCH`.

- [ ] **Step 6: Tilføj dblink-racetest**

To transaktioner forsøger at acceptere to forskellige record-placementforslag med samme `(source_record_id,scheme_entry_id)` fra version 1. Den ene holdes åben; den anden skal blokere på parent-recordlåsen og efter første COMMIT fejle `EVIDENCE_PLACEMENT_ALREADY_ACCEPTED`. Assertér præcis ét current accepted placement og ingen event fra den tabende transaktion.

- [ ] **Step 3: Implementér regellinje, current-view og add-version-funktion**

```sql
CREATE TABLE private.interpretation_promotion_rule_line (
  rule_key text PRIMARY KEY CHECK (btrim(rule_key)<>''),
  predicate text NOT NULL UNIQUE CHECK (btrim(predicate)<>''),
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE VIEW private.interpretation_promotion_rule_current AS
SELECT DISTINCT ON (rule.rule_key) rule.*
  FROM private.interpretation_promotion_rule rule
 ORDER BY rule.rule_key,rule.rule_version DESC;
```

Fjern `interpretation_promotion_rule_one_active_predicate`. Tilføj FK fra `(rule_key,predicate)` til regellinjen via en `UNIQUE(rule_key,predicate)` på line-tabellen. `add_interpretation_promotion_rule_version` låser line-rækken `FOR UPDATE`, kræver identisk predicate, beregner `max(rule_version)+1` og indsætter immutable version. Line-tabellen er registry/current-lock, ikke en mutable statusprojektion.

I fresh schema indsættes de fem eksisterende `rule_key`/predicate-par i
line-tabellen før version 1-rækkerne indsættes i promotionregel-tabellen og før
FK'en valideres. Line-tabellen får append-only trigger, RLS og samme private ACL
som regelversionerne.

Preview-hash/profile-hash skal fortsat inkludere konkret `rule_key` og `rule_version`; final batch genberegner efter lock.
